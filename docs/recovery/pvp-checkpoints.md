# PvP checkpoint capture pilot

This document describes the original **capture-only pilot**, disabled by default. Its flag does not enable player recovery. The subsequent [private PvP recovery implementation](pvp-recovery.md) has a separate opt-in flag, authenticated participant binding and reconnection flow. Neither feature can protect an already running match that started without checkpoints.

## Delivered behavior

`PLAYMAT_PVP_CHECKPOINTS=capture` opts an isolated assembled engine into capture. Any other value, including an unset variable, leaves the feature off without opening a database. The initial scope is Java games with exactly two human seats outside tournaments, with turn rollback disabled. An MCP player occupies a human seat. Solo saves retain their existing behavior. Rust-hosted games have no Java snapshot callback and are outside this pilot.

`TableController` installs a `GameOptions.turnSnapshots` consumer before starting the game. It uses the existing `GameSnapshot` boundary immediately before the turn's untap step. The full snapshot includes private hands, library order, card objects, exile, effects, triggers, watchers and the game's RNG state. This is not a replay of recorded views or logs.

One private SQLite row per original match ID contains:

| Field | Meaning |
| --- | --- |
| `match_id`, `table_id`, `game_id` | Original engine IDs, also used by replay/product metadata; never regenerated by the store |
| `game_number`, `turn`, `revision`, `committed_at` | Exact captured boundary and successful database revision |
| `status` | `capture_only`, `between_games`, or `completed`; none means resumable |
| `format`, `engine`, `checksum` | Envelope version, SHA-256 of the assembled engine/plugin JARs, framed checksum of context and snapshot |
| `context`, `snapshot` | Private serialized match configuration and full engine snapshot |

Context preserves current deck/sideboard lists, score, draws, game number, match options, player IDs and frozen priority/buffer clocks. The copy of `MatchOptions` has its table password cleared without changing the live options. Session user IDs and display names are diagnostic data, **not authorization**. There are no tokens or account credentials in this context.

Serialization and the SQLite write run synchronously on the game thread. `journal_mode=DELETE` and `synchronous=FULL` mean the method returns after SQLite commits; there is no asynchronous writer queue and no in-memory turn is called confirmed. Storage errors retain the previous confirmed row and emit a payload-free warning. Capture failure does not stop play. This pilot has no player-facing checkpoint acknowledgment.

The database is `db/pvp-checkpoints.db`; the all-in-one image's existing db symlink places it on `/var/lib/playmat/db`. Database and lock files require owner-only POSIX permissions. A process-held file lock rejects another capture writer using the same database. A process death releases the lock; SQLite recovers its rollback journal on reopen. The database must be on a local durable filesystem with working SQLite sync/locking semantics. A volume preserves data across process/container replacement, not loss of the volume itself. No remote backup/replication or retention policy is implemented here; do not enable long-running capture without a disk and private-backup policy. Never copy this database into the web root, replay object store, support export, logs or repository.

The read helper is package-private, used only by trusted tests/diagnostics. It rejects a different engine/format or checksum failure before deserialization. The fingerprint covers the shipped `lib` and `plugins` JARs, not an arbitrary IDE classpath; capture refuses to initialize without the assembled directories or when extension packages are installed. There is no migration across engine builds and no untrusted snapshot upload. Synchronous serialization, snapshot decoding for frozen clock metadata and disk sync add work at each turn boundary; no latency benchmark or production resource budget has been established.

The normal game-end hook marks the row `between_games` or `completed` before the next game/sideboarding begins. Checkpoints from a completed match cannot overwrite that terminal row, and an old game's end notification cannot invalidate a newer game's checkpoint. Sideboarding, mulligan decisions before the first turn, turn rollback and a crash between the final game decision and this lifecycle write remain outside recovery guarantees. A future restore adapter must not infer resumability merely from this pilot's status.

## Integration checklist recorded at the capture-only milestone

The following historical design checklist motivated the later [recovery implementation](pvp-recovery.md). Consult that guide for current behavior and limits.

1. **Participant identity at seat admission.** Persist immutable product `accountId` plus the precise admitted browser seat or agent grant/connection identity for both seats, bound to the engine session that actually joined. Resolve this during authenticated admission, not by looking up display names after a restart. Existing `User` IDs are process-local; `viewerNames()` and the archive's name-based access checks are insufficient. This branch changes no OAuth rules or product identity interfaces.
2. **Stable private match route.** Use the original product/engine match ID for a route such as `/matches/:id`, authorized against those immutable participants. Keep original public table/game IDs in an explicit mapping to newly allocated engine IDs; never reuse a public ID as proof of access. Replays and game numbering must include recovery generations without double-counting results. No such route or mapping adapter is supplied here.
3. **Durable recovery state machine.** Separate a currently live engine owner from an interrupted match; use PostgreSQL transactional compare-and-set with fencing/generation and a unique active recovery claim. Two simultaneous reconnects must share one waiting generation and one table. Record a prepared restore before creating sessions, validate/deserialise the whole snapshot and configuration before publishing the table, and recover a crashed claimant without creating two live games. The local writer lock in this pilot does not provide that distributed claim protocol.
4. **Seat reservation and reconnect.** Reserve each new seat to the saved participant identity; require both current authenticated participants to reconnect and acknowledge the durable rollback boundary. Repeated browser/MCP reconnects must be idempotent. Revoked grants, disabled accounts, unrelated actors and a participant asking for the other seat must fail closed. Original participant hands and full checkpoints must never become spectator/public payloads. No restore endpoint exists in this branch, including when capture is on.
5. **Explicit clock policy.** Proposed policy: pause downtime and reconnect waiting time; restore each priority/buffer clock to its value at the confirmed turn boundary and start ticking only when both reserved seats have attached. The interrupted turn's decisions and time consumption are discarded together. Existing `playFromSnapshot` does not implement that two-participant barrier. Clock values are captured/tested here; resumed clock behavior is not implemented.
6. **Lifecycle completeness.** Atomically persist sideboarding, submitted decks, chooser, draws, scores and pending next-game state; define crash handling before a first checkpoint and around game completion/result posting. Add rollback branch/generation handling before allowing turn rollback. Validate game options, participant remapping, game number and all objects together, and fail visibly without exposing a half-loaded table. Keep older incompatible checkpoints private for explicit operator handling.
7. **Visible semantics.** A successful future reconnect must say: “Resuming from the start of the last durably confirmed turn N. Later decisions were lost.” Report the stored confirmed turn, never the latest attempted snapshot or archive log turn. Display unavailable/incompatible states clearly. Confirming a snapshot does not promise replay-equivalent future choices or stable newly generated IDs.

## Local verification only

Use a separate checkout/worktree and dedicated dependency cache. Do not attach production volumes, reuse live service containers, use real credentials, expose ports or run deployment scripts.

With the repository's prebuilt card dependency and Maven dependencies already in a dedicated cache:

```sh
docker run --rm --network none --hostname localhost \
  -v playmat-recovery-maven:/root/.m2 \
  -v "$PWD:/source" -w /source -e MAVEN_OPTS=-Xmx1500m \
  maven:3.9-eclipse-temurin-17 \
  mvn -o -B -q -pl 'Mage.Server,!Mage.Sets' -am test \
  -Dtest=CheckpointStoreTest,SoloFoundationsTest \
  -Dsurefire.failIfNoSpecifiedTests=false \
  '-DargLine=-Dfile.encoding=UTF-8 -Dh2.bindAddress=127.0.0.1'
```

`CheckpointStoreTest` starts a separate JVM using two actual `HumanPlayer` objects (one named as an MCP fixture), captures the fixture, waits for the confirmed commit, kills the writer forcibly and verifies the row in another fresh JVM. Assertions check ordered library names, private hands, two exiled cards, a continuous effect, watcher state, RNG continuation, scores, sideboards, options and clocks. A separate child modifies both payloads in an uncommitted SQLite transaction; killing it verifies the previous complete checkpoint survives. Tests also cover concurrent store ownership, repeated reopen, incompatible envelope/database/engine versions, corrupt bytes, private file modes, symlink rejection, terminal state and changed binary fingerprints.

These are storage/snapshot fixture tests, **not** a live browser/MCP game reconnection test or a whole-server restart acceptance test. Before shipping recovery, run an isolated all-in-one server with two authenticated product accounts and a real MCP client, kill/recreate that engine process, test simultaneous/repeated reconnects and denied unrelated/revoked clients, and verify continued gameplay, effects/triggers, identifiers, private projections, result accounting, sideboarding and ticking clocks. That acceptance test must wait for the missing identity/restore interfaces above.
