# Private Magic playtesting beta

Status: product decisions confirmed on 2026-11-16. Implementation and acceptance evidence are pending.

This specification supersedes the earlier [exploration brief](../../plans/one-shot-grill-me.md). Playmat is the product base and XMage is the rules engine. Publish product source in the public fork. Run the service and keep its data private on Railway. The beta has no ladder. The public landing and account registration follow the [public signup specification](public-signup.md).

## PM-UI — An Arena-inspired board on desktop and phone

**PM-UI-01. Turn and priority.** Place a horizontal phase strip immediately above the primary action at the bottom right. Show five symbols for Inicio, Principal I, Combate, Principal II and Fin, highlight the engine's current phase, and center its single-line label above the symbols. Show the relevant substeps during combat. Keep the active turn and priority available through the player indicators and accessible labels. Display mandatory decisions, such as “Elige bloqueadores”, alongside the controls that answer them.

**PM-UI-02. Primary action.** On an ordinary priority prompt, display “Pasar” when the stack has an item, with the top item visible in the stack. When the stack is empty, use the contextual “Ir a <fase>” label for the next eligible destination and indicate that the action passes priority. Keep the primary action's dimensions stable as its label changes. Obey configured stops and render the confirmed phase from XMage, including when the opponent responds, a trigger appears, or a mandatory prompt interrupts advancement. For a specific decision, use the relevant action, such as confirming attackers or choosing targets. Use one pending response per engine prompt.

**PM-UI-03. Passing and stops.** Auto-pass empty priority windows by default, including windows with mana abilities alone when no relevant decision is pending. Preserve manual response windows, mandatory decisions and configured stops. Expose explicit longer skips separately, and keep Control total accessible. Space passes a single window when the board owns keyboard focus. A phase-symbol tap or click sets a stop for the current turn. Persistent settings support separate stops for your turns and the opponent's turns. A stop marker is visually distinct from the lit current phase. Treat both as accessible state.

**PM-UI-04. Board and motion.** Use one original Arena-inspired tabletop. Keep hands, lives and zones legible, creatures near the middle, lands behind them, and the stack on the side while occupied. On narrow screens, keep the important state reachable with touch. Open a compact participant chat from a labeled control on the board and keep the game log in the same panel. Choose targets and declare attackers and blockers on the board. Use dialogs for mulligans, modes and selection from other zones, with inspection when the decision needs it. Centralize overlay order for the board, stack, previews, dialogs and effects. Keep short card, resolution, combat and damage animations, with reduced-motion support. Animate confirmed live draws from the player's library to their hand after the opening hand. Defer 3D scenes, particles and custom per-card effects.

**PM-UI-05. Mobile coverage.** Support the full invited Bo3 flow in desktop and mobile browsers from sign-in to replay, including text and touch entry, card inspection, targets, sideboarding and chat. Desktop offers full screen. Reuse the existing PWA where supported, with the game and its dialogs usable in installed mode. Use safe-area and dynamic viewport layouts, and preserve game state across viewport changes and browser rejoin.

Reuse [phase definitions](../../../Mage.Web.Client/src/app/match/PhaseLadder.tsx), [derived interactions](../../../Mage.Web.Client/src/core/game/interaction.ts), [board](../../../Mage.Web.Client/src/app/match/MatchStage.tsx) and [motion](../../../Mage.Web.Client/src/app/match/Vfx.tsx).

## PM-GAME — Between-game flow and consensual rollback

**PM-GAME-01. Match.** Create private 1v1 best-of-three matches with Standard, Pioneer or Modern rules. The host starts after both seats have validated decks and are ready. Track match score and distinct game IDs. After each nonfinal game, each seat can submit a legal sideboard change from its own fixed main and sideboard pool. Enforce conservation of that card multiset on both autosave and final submission, including direct RPC and MCP calls. Advance when both seats are ready, honoring engine-supported sideboard deadlines and surfacing any default submission. Keep sideboarding drafts and the submitted configuration private. Record the exact configuration used by each seat for each game without editing the library deck. Finish when XMage determines the match winner. This covers human, MCP-controlled and native XMage AI seats.

**PM-GAME-02. Rollback.** Enable rollback requests for practice matches. Offer the start of the current or previous turn when an engine snapshot exists. Require the other seat's affirmative vote. Bind the vote to the requested game, seat and turn so progression cannot change the requested destination. Apply only once, and preserve play when declined, expired or stale. Invalidate outstanding decision IDs, waits and sequences on an approved rollback. The replay marks the rewind and the canonical line resumes from the restored state. A native AI opponent uses the engine's supported vote behavior, which must be verified before claiming rollback for that matchup type.

Reuse [match creation](../../../Mage.Web.Client/src/app/screens/TablesScreen.tsx), [between-game sideboarding](../../../Mage.Web.Client/src/app/events/BuildScreen.tsx) and [engine match control](../../../Mage.Server/src/main/java/mage/server/TableController.java).

## PM-DATA — Accounts, library and durable match history

**PM-DATA-01. Accounts and invitations.** An operator can manually provision a username and credential through a private administrative path. A visitor can register by verifying their email and choosing a password through the [public signup flow](public-signup.md). Both use the same password sign-in. Provision the private engine principal alongside the product account or allow its creation only through verified trusted ingress. Enforce this identity on HTTP and WebSocket and strip any client-supplied trusted headers. Invites expire and reserve one guest seat. [Named invites and unlisted links](deck-import-and-invitations.md) enforce their respective seat admission rules. Open directly to deck selection after sign-in. Lobby, live game, chat, history and downloads enforce membership on the server. Invalidate credentials on revocation and verify session resumption after a normal reconnect.

For an MCP rival table, the host selects MCP mode. An OAuth client connected to the same Playmat account can discover and claim the rival's seat. The host can also share the private link with that client. Bind the claim atomically. The agent may supply a display name when joining. Playmat uses the internal engine identity for membership and the account identity for library ownership. The table explicitly shows when the MCP rival is seated and the host can start.

For a new MCP table, the host chooses Quiet, Chatty for friendly commentary, or Coach for feedback based on public play. Quiet is the default for both new and existing tables without a saved choice. MCP join and game state communicate the saved preference to the agent throughout the match, including after sideboarding. The join page shows the selected mode, the MCP endpoint and the resource URIs for setup, card search, turn planning and rules. The host can copy either the join URL or ready-to-share agent instructions. Friend and native AI tables do not choose an MCP chat mode.

Coach accompanies the human with at most one concretely supported strong public opportunity during their turn,
then a short review after each completed human turn: a justified better alternative and why, or a specific,
qualified acknowledgement when no improvement is identified. Tone is warm and lightly playful. Instructions
appear in MCP initialization, the getting-started guide and the copied Coach invitation. The existing connected
model produces the feedback through participant chat, without pausing engine decisions, extra evaluation
infrastructure or new hand permissions. Hidden rival information, private looks and later reveals must not be
used to manufacture superiority or expose cards. Missing observations are acknowledged rather than scored.

Starting MCP play from Home or selecting an MCP rival in the host form opens a connection guide before table creation. The guide provides the remote endpoint, account OAuth instructions and how the agent can find the invitation. The host can skip automatic display on this browser, reopen the guide in the host form, and restore automatic display.

**PM-DATA-02. Library.** One shared browser and MCP library supports search, import, create, edit, duplicate and validation. Save browser drafts and imports with their selected format, or use Freeform if no format is provided. Filter and validate Standard, Pioneer and Modern using the pinned engine's card coverage and legality rules. Distinguish a card's identity, its printing and the instance in the game. Use immutable deck revisions and explicit edit versions so concurrent edits cannot silently overwrite each other. Authorize reads and writes by owner. Fix the submitted version to the match and keep sideboard changes for the individual game.

**PM-DATA-03. Persistence.** Railway PostgreSQL owns product accounts, authorization, decks and their revisions, invites, matches, game participants, results, typed events and replay metadata. Existing XMage stores for internal engine purposes can remain. Keep one authoritative writer and read path per product record. Use relational columns and constraints for identity, lifecycle and queryable fields. Payloads that are intrinsically variable can be versioned in the event or replay archive. Document how browser paths and MCP share the same services and how engine identities are provisioned, with no second visible login.

**PM-DATA-04. Replays and exports.** Capture replay snapshots and game log in server order. Exclude participant chat from capture in the live-only chat policy. Use private S3 objects for compressed, versioned artifacts. Persist capture and upload intent, protect incomplete uploads from native replay pruning, retry idempotently, verify checksums and track ready, pending and partial separately from match status. Retain the 20 most recent closed matches per account across the human and agent seats, ordered by match start time. Count each match once and keep active matches outside the quota. Apply the same retained set before format filters, pagination and direct archive access. An operator can exempt a specific account. When physical cleanup is enabled, remove closed match data and queue replay object deletion only if no participant account retains it. Preserve an interrupted match record and any recoverable partial capture with explicit status, including truncation. Open completed replays after deploy or browser reconnect. Provide authorized game-by-game and multi-match analysis through filtered, cursor-paginated MCP data and downloadable ZIP bundles with a manifest, per-game JSONL and a CSV summary. Exports include the requesting player's own authorized data and public match information. Authorize at both generation and fetch, and keep raw archive keys and frames containing both hands private. Apply the same redaction to initial and sideboarded deck lists, replay, stats, exports and MCP tool results.

**PM-DATA-05. Analytics and chat.** Record format, match and game results, starting player, mulligans, the engine turn at finish, end reason and exact deck revision. Provide aggregated results by format and deck revision or privacy-safe matchup label, plus individual game details. Define play/draw at the game level. Distinguish concession, interrupted games and completed results. Record a typed rewind marker when state is restored and exclude abandoned branches from aggregates. Provide live chat for participants in the web UI and MCP. Keep the game log in the replay. Chat transcript retention is deferred by default.

Existing [trusted sign-on](../../TrustedHeaderAuth.md) and [replay recorder](../../../Mage.Server/src/main/java/mage/server/replay/ReplayRecorder.java) are integration points. [Railway PostgreSQL](https://docs.railway.com/databases/postgresql) · [S3 versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)

## PM-MCP — Private agent access and turn sequences

**PM-MCP-01. Identity and transport.** Expose an authenticated Streamable HTTP URL for OAuth-capable MCP clients with scoped, revocable agent credentials. Agent and human use distinct game seats. A user can delegate library and history access explicitly to an agent without granting access to another participant's hand, library, private deck list or pending prompt. Treat chat, Oracle text and external archetype data as data. Use typed commands with explicit game, seat and ownership verification. Reuse the browser's engine-validated game operations. In a supported browser, WebMCP lets the signed-in invited friend join with their selected deck. The live seat offers only its visible state and choices. Remove tools when the route or session loses eligibility. Keep the invite's authorization and the current prompt checks in the existing join and game operations.

**PM-MCP-01a. Observe a delegated human seat.** When the match permits an agent to play for the human, the signed-in human's browser shows the live board, their own hand and a read-only indicator, including before the agent connects. Opening the game, reconnecting, reloading and entering sideboarding preserve this mode. The browser can refresh the board and navigate away while the match continues. It withholds gameplay controls, shortcuts, automatic answers, chat input, rollback votes and sideboard edits. It waits to verify the seat before enabling any input. Other human seats and tables with the option off retain their normal controls.

**PM-MCP-01b. Live audience commentary.** A spectator sees a recently committed agent line’s shareable explanation by the acting seat, matched by game and player ID. The broadcast chat interleaves these audience notes with both players’ table chat in chronological order. Each entry identifies its type and speaker. Reconnecting does not repeat messages. Card references support previews. Spectators can read the feed without sending messages. Only table dialogue reaches the opponent.

**PM-MCP-01c. Independent table conversation.** Both playing seats can run `wait_for_chat` alongside an active game command and answer with `send_chat`. A game-scoped chat cursor supports catch-up and deduplication independently of the gameplay cursor. The listener returns opponent speech or a timeout or game boundary. Chat never submits a choice or advances an active line. Reconnecting participants may retrieve up to 50 recent public table messages. Clients with sequential tool calls can read `list_chat` when a gameplay receipt reports a newer `chatCursor`.

**PM-MCP-02. Tool families.** Provide typed schemas, bounded queries and actionable errors. Select and validate resource IDs after authenticating the caller.

| Capability | Tools |

**PM-MCP-03. Decision loop.** `wait_for_decision` accepts a seat-scoped cursor and a bounded timeout. It wakes on an actionable prompt, relevant game status, explicit invalidation or match end, and distinguishes timeout from a disconnected session. A decision identifies the game, seat, state revision and current prompt. A retry with the same idempotency key cannot play twice. A stale answer, unauthorized action or superseded seat is rejected. Use authoritative game state and prompts rather than guessing from logs.

**PM-MCP-04. Sequences.** Accept one finite, observable plan per seat starting from a known game revision. Prefer [semantic `play_line` intentions](play-line.md): play a named visible card, choose guarded costs/modes, declare attackers, and select a safe finish. The MCP inserts legal ordinary passes until the next intention; exact priority predictions and pass steps are not required. Existing visible stack objects and exact declared own casts/triggers may resolve. Rival non-pass actions, relevant new information, configured stops and unknown mandatory decisions interrupt. See [whole-turn plans](whole-turn-plans.md) for causal evidence, Ward and auto-target safeguards. Legacy steps can conditionally answer a prompt, hold for a requested number of seconds before acting, or pass until a specific phase, priority or stop condition. The default preserves new meaningful response windows. Allow the agent to request skipping optional windows intentionally. Required choices and configured stops still stop the sequence. Bound waits by a server maximum and any game deadline, and return the effective delay. A delay holds the current decision without modifying the clock and remains cancelable. Before each action, verify the current prompt, authorization and preconditions. Interrupt and wake the agent if the rival responds unexpectedly, an action is unavailable, ownership changes, the plan times out, the target is unreachable, or a rewind or game transition invalidates the sequence. Expose completed steps, reason for stopping and a fresh cursor. Cancel before applying uncommitted actions and retain actions already accepted by XMage. Reconcile an uncertain acknowledgement before resuming. Expire queued actions on process restart.

An answer may name the exact currently valid choice or select a visible card or label that resolves to exactly one choice. The agent can mark its own planned cast so a guarded sequence can play a land, cast the spell and pay its mana without a round trip for each decision. Identify the planned spell by its card and controller, and stop when any unrelated card or effect changes the stack. Wait through transient state updates until a typed actionable prompt is available.

**PM-AC-09-CREATURE.** A declared own creature cast may resolve into its controller's battlefield and continue to a legal guarded attack in the same turn when `allowPlannedResolutions` is enabled. Public resolution evidence must cover permanent spells as well as instants and abilities, once per public stack object, before resolution effects begin. New own permanents, spent mana and loss of the cast card from hand do not by themselves imply a rival action. Missing evidence, rival actions/responses and unannounced triggers still interrupt before the attack. Resolution observation must not create rules events or reveal hidden card identities.

See [the permanent-resolution regression evidence](creature-resolution-evidence.md) for the observed failure, exact tests and remaining integration boundary.

**PM-MCP-05. AI seats.** Play against either the native XMage AI or an external Codex session through the private URL. Native AI requires no Codex connection. Publish four authenticated MCP resources readable before joining. The versioned guide bundle returns all four in one tool call. Cover seat setup and chat, card and archetype lookup, conditional turn plans using engine-confirmed choices, and the official Comprehensive Rules with a numbered index. Advertise their URIs in MCP initialization and on the invitation page. A hosted LLM opponent and benchmark claims about playing strength are outside this cut.

**PM-MCP-06. Post-match evaluation.** Offer a discoverable review prompt and tools for history-scoped agents. Accept a completed archived game and extract bounded pre-action positions for observed land plays and spells cast from the player's hand. Exclude rewound branches, later draws, outcome and hidden opponent information. The connected LLM compares the played move with plausible legal alternatives and replies using only that evidence. Reject unknown and duplicate replay positions when producing a report. Calculate estimated accuracy as 100 minus the mean relative quality lost to the judge's best alternative over medium or high-confidence positions. Return the measured coverage and no score when evidence is insufficient. The report does not modify match results or statistics.

**PM-MCP-07. Agent events.** A browser player can create an MCP table for their own account, including before connecting a client. The OAuth agent for that account alone can discover and claim the rival's place. Deliver `game.invitation.created` to the account's subscribed clients when the table is created. Publish `game.decision.required` for a rival's new actionable prompt, including sideboarding, with its game ID, decision ID, cursor and prompt kind. Cancel pending delivery after the prompt changes and bound its lifetime. Authenticate event discovery and subscriptions through the same MCP endpoint. Verify an HTTPS callback before delivering signed events. Keep active subscriptions through application restarts and check continuing authorization on delivery. Match and hand details stay behind existing tools.

**PM-MCP-08. OAuth connection and self-play.** The user signs in with their Playmat account and authorizes a client. The connection uses that account's library. Playmat assigns a distinct internal XMage identity automatically so the agent can play the rival while the user stays in the same account. The rival can choose its visible name when joining and can chat as that rival during the match. Client access remains bound to the account and authorized scopes. Use authorization-code OAuth with S256 PKCE, a registered client and exact callback validation.

### Decisions applied as beta defaults

The host starts manually. Replay access uses the player's perspective and no automatic opponent-hand reveal. Completed replays have no automatic expiration for the beta. Chat is live only. ### Match-scoped human MCP control

Private Home opens with MCP rival selected. The four equal-width choices are MCP rival, a friend, practice and BOT. A human host can opt in to agent play for that match. The choice starts off each time. Creation records it before play and participants can identify the enabled human seat at the table, during play and in history. The human's normal identity and deck library survive the match. An authenticated agent can create each mode using the human library, with or without permission to play. An enabled human seat and the account's MCP player receive separate decisions and hands. The browser observes the delegated human seat, including its private hand, from game start through sideboarding and match completion. While delegated, only MCP may take gameplay actions, even during agent disconnection or browser reconnection. A browser observing one match can still play a different match where it controls its seat. Both agent roles use the same gameplay methods, action schemas, receipts and wait cursors. Older matches default to no delegation.

Agents may attach a short, shareable explanation to an accepted line. Its seat, game and command identify it across retries. The authorized replay presents the explanation at the line with a visibility switch. Card references in review prose and mulligan evidence support pointer, keyboard and touch previews, including a specified card face.
