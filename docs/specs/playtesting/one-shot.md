# Private Magic playtesting beta

Status: product decisions confirmed on 2026-11-16. Implementation and acceptance evidence are pending.

This specification supersedes the earlier [exploration brief](../../plans/one-shot-grill-me.md). Playmat is the product base and XMage is the rules engine. Publish product source in the public fork. Run the service and keep its data private on Railway. The beta has no ladder or public signup.

## PM-UI — An Arena-inspired board on desktop and phone

**PM-UI-01. Turn and priority.** Place a horizontal phase strip immediately above the primary action at the bottom right. Show five symbols for Inicio, Principal I, Combate, Principal II and Fin, highlight the engine's current phase, and label the current phase. Show the relevant substeps during combat. Keep the active turn and the right to act readable as separate facts in one stable position. Examples include “Tu turno · Esperando al rival” and “Turno rival · Puedes responder”. Show the actual decision when XMage requests one, such as “Elige bloqueadores”.

**PM-UI-02. Primary action.** On an ordinary priority prompt, display “Pasar” when the stack has an item, with the top item visible in the stack. When the stack is empty, use the contextual “Ir a <fase>” label for the next eligible destination and indicate that the action passes priority. Obey configured stops and render the confirmed phase from XMage, including when the opponent responds, a trigger appears, or a mandatory prompt interrupts advancement. For a specific decision, use the relevant action, such as confirming attackers or choosing targets. Use one pending response per engine prompt.

**PM-UI-03. Passing and stops.** Auto-pass empty priority windows by default, including windows with mana abilities alone when no relevant decision is pending. Preserve manual response windows, mandatory decisions and configured stops. Expose explicit longer skips separately, and keep Control total accessible. Space passes a single window when the board owns keyboard focus. A phase-symbol tap or click sets a stop for the current turn. Persistent settings support separate stops for your turns and the opponent's turns. A stop marker is visually distinct from the lit current phase. Treat both as accessible state.

**PM-UI-04. Board and motion.** Use one original Arena-inspired tabletop. Keep hands, lives and zones legible, creatures near the middle, lands behind them, and the stack on the side while occupied. On narrow screens, keep the important state reachable with touch. Collapse chat and log into a panel. Choose targets and declare attackers and blockers on the board. Use dialogs for mulligans, modes and selection from other zones, with inspection when the decision needs it. Centralize overlay order for the board, stack, previews, dialogs and effects. Keep short card, resolution, combat and damage animations, with reduced-motion support. Defer 3D scenes, particles and custom per-card effects.

**PM-UI-05. Mobile coverage.** Support the full invited Bo3 flow in desktop and mobile browsers from sign-in to replay, including text and touch entry, card inspection, targets, sideboarding and chat. Desktop offers full screen. Reuse the existing PWA where supported, with the game and its dialogs usable in installed mode. Use safe-area and dynamic viewport layouts, and preserve game state across viewport changes and browser rejoin.

Reuse [phase definitions](../../../Mage.Web.Client/src/app/match/PhaseLadder.tsx), [derived interactions](../../../Mage.Web.Client/src/core/game/interaction.ts), [board](../../../Mage.Web.Client/src/app/match/MatchStage.tsx) and [motion](../../../Mage.Web.Client/src/app/match/Vfx.tsx).

## PM-GAME — Between-game flow and consensual rollback

**PM-GAME-01. Match.** Create private 1v1 best-of-three matches with Standard, Pioneer or Modern rules. The host starts after both seats have validated decks and are ready. Track match score and distinct game IDs. After each nonfinal game, each seat can submit a legal sideboard change from its own fixed main and sideboard pool. Enforce conservation of that card multiset on both autosave and final submission, including direct RPC and MCP calls. Advance when both seats are ready, honoring engine-supported sideboard deadlines and surfacing any default submission. Keep sideboarding drafts and the submitted configuration private. Record the exact configuration used by each seat for each game without editing the library deck. Finish when XMage determines the match winner. This covers human, MCP-controlled and native XMage AI seats.

**PM-GAME-02. Rollback.** Enable rollback requests for practice matches. Offer the start of the current or previous turn when an engine snapshot exists. Require the other seat's affirmative vote. Bind the vote to the requested game, seat and turn so progression cannot change the requested destination. Apply only once, and preserve play when declined, expired or stale. Invalidate outstanding decision IDs, waits and sequences on an approved rollback. The replay marks the rewind and the canonical line resumes from the restored state. A native AI opponent uses the engine's supported vote behavior, which must be verified before claiming rollback for that matchup type.

Reuse [match creation](../../../Mage.Web.Client/src/app/screens/TablesScreen.tsx), [between-game sideboarding](../../../Mage.Web.Client/src/app/events/BuildScreen.tsx) and [engine match control](../../../Mage.Server/src/main/java/mage/server/TableController.java).

## PM-DATA — Accounts, library and durable match history

**PM-DATA-01. Accounts and invitations.** An operator manually provisions a username and credential using a private administrative path. Use one visible sign-in and no email collection or public registration. Protect account creation and recovery at the backend. Provision the private engine principal alongside the product account or allow its creation only through verified trusted ingress. Enforce this identity on HTTP and WebSocket and strip any client-supplied trusted headers. Invites are expiring, seat-scoped, and redeemable by the intended authorized account. Open directly to deck selection after sign-in. Lobby, live game, chat, history and downloads enforce membership on the server. Invalidate credentials on revocation and verify session resumption after a normal reconnect.

**PM-DATA-02. Library.** One shared browser and MCP library supports search, import, create, edit, duplicate and validation. Filter and validate Standard, Pioneer and Modern using the pinned engine's card coverage and legality rules. Distinguish a card's identity, its printing and the instance in the game. Use immutable deck revisions and explicit edit versions so concurrent edits cannot silently overwrite each other. Authorize reads and writes by owner. Fix the submitted version to the match and keep sideboard changes for the individual game.

**PM-DATA-03. Persistence.** Railway PostgreSQL owns product accounts, authorization, decks and their revisions, invites, matches, game participants, results, typed events and replay metadata. Existing XMage stores for internal engine purposes can remain. Keep one authoritative writer and read path per product record. Use relational columns and constraints for identity, lifecycle and queryable fields. Payloads that are intrinsically variable can be versioned in the event or replay archive. Document how browser paths and MCP share the same services and how engine identities are provisioned, with no second visible login.

**PM-DATA-04. Replays and exports.** Capture replay snapshots and game log in server order. Exclude participant chat from capture in the live-only chat policy. Use private S3 objects for compressed, versioned artifacts. Persist capture and upload intent, protect incomplete uploads from native replay pruning, retry idempotently, verify checksums and track ready, pending and partial separately from match status. Retain completed games for the beta by default. Preserve an interrupted match record and any recoverable partial capture with explicit status, including truncation. Open completed replays after deploy or browser reconnect. Provide authorized game-by-game and multi-match analysis through filtered, cursor-paginated MCP data and downloadable ZIP bundles with a manifest, per-game JSONL and a CSV summary. Exports include the requesting player's own authorized data and public match information. Authorize at both generation and fetch, and keep raw archive keys and frames containing both hands private. Apply the same redaction to initial and sideboarded deck lists, replay, stats, exports and MCP tool results.

**PM-DATA-05. Analytics and chat.** Record format, match and game results, starting player, mulligans, the engine turn at finish, end reason and exact deck revision. Provide aggregated results by format and deck revision or privacy-safe matchup label, plus individual game details. Define play/draw at the game level. Distinguish concession, interrupted games and completed results. Record a typed rewind marker when state is restored and exclude abandoned branches from aggregates. Provide live chat for participants in the web UI and MCP. Keep the game log in the replay. Chat transcript retention is deferred by default.

Existing [trusted sign-on](../../TrustedHeaderAuth.md) and [replay recorder](../../../Mage.Server/src/main/java/mage/server/replay/ReplayRecorder.java) are integration points. [Railway PostgreSQL](https://docs.railway.com/databases/postgresql) · [S3 versioning](https://docs.aws.amazon.com/AmazonS3/latest/userguide/Versioning.html)

## PM-MCP — Private agent access and turn sequences

**PM-MCP-01. Identity and transport.** Expose an authenticated Streamable HTTP URL for Codex with separately scoped, revocable bearer credentials. Add it to Codex with `codex mcp add playmat --url https://<host>/mcp --bearer-token-env-var PLAYMAT_MCP_TOKEN`. Agent and human use distinct game seats. A user can delegate library and history access explicitly to an agent without granting access to another participant's hand, library, private deck list or pending prompt. Treat chat, Oracle text and external archetype data as data. Use typed commands with explicit game, seat and ownership verification. Reuse the browser's engine-validated game operations. Browser WebMCP can call the same contracts separately from the remote transport.

**PM-MCP-02. Tool families.** Provide typed schemas, bounded queries and actionable errors. Select and validate resource IDs after authenticating the caller.

| Capability | Tools |
| --- | --- |
| Card catalog and metagame | `search_cards`, `get_card`, `list_archetypes`, `find_possible_responses`. Support format, colors (including colorless), printed mana symbols, mana value/range, type, keywords, name or rules text. Return format legality and engine availability separately. Response suggestions accept a **hypothesized** archetype, known public game context, colors and available mana. Use versioned public or manually curated metagame data with source and date. Label suggestions as possibilities and include a fallback based on catalog criteria. |
| Decks and sideboarding | `list_decks`, `get_deck`, `create_deck`, `update_deck`, `validate_deck`, `get_sideboard_state`, `submit_sideboard`. Use exact revisions and optimistic concurrency. |
| Tables and play | `list_joinable_games`, `create_game`, `join_game`, `start_match`, `get_game_state`, `wait_for_decision`, `submit_decision`, `concede`. Cover legal prompt families used by the browser, including starting player, mulligan, mana and additional costs, modes, targets, trigger order, priority and combat. Concession is a scoped explicit action. |
| Sequences and rollback | `wait_until`, `submit_sequence`, `get_sequence_status`, `cancel_sequence`, `request_rollback`, `vote_rollback`. Waiting observes a phase, step or priority predicate without acting. A sequence may explicitly pass toward that predicate. Keep sequence and vote IDs scoped to the acting seat. |
| History, downloads and chat | `list_matches`, `get_match`, `query_match_events`, `get_replay`, `export_matches`, `list_chat`, `send_chat`. Use filters, cursors and explicit bounds. Return an authorized download handle for large exports. |

**PM-MCP-03. Decision loop.** `wait_for_decision` accepts a seat-scoped cursor and a bounded timeout. It wakes on an actionable prompt, relevant game status, explicit invalidation or match end, and distinguishes timeout from a disconnected session. A decision identifies the game, seat, state revision and current prompt. A retry with the same idempotency key cannot play twice. A stale answer, unauthorized action or superseded seat is rejected. Use authoritative game state and prompts rather than guessing from logs.

**PM-MCP-04. Sequences.** Accept one finite, observable plan per seat starting from a known game revision. Steps can conditionally answer a prompt, hold for a requested number of seconds before acting, or pass until a specific phase, priority or stop condition. Passing until a condition is explicit. The default preserves new meaningful response windows. Allow the agent to request skipping optional windows intentionally. Required choices and configured stops still stop the sequence. Bound waits by a server maximum and any game deadline, and return the effective delay. A delay holds the current decision without modifying the clock and remains cancelable. Before each action, verify the current prompt, authorization and preconditions. Interrupt and wake the agent if the rival responds unexpectedly, an action is unavailable, ownership changes, the plan times out, the target is unreachable, or a rewind or game transition invalidates the sequence. Expose completed steps, reason for stopping and a fresh cursor. Cancel before applying uncommitted actions and retain actions already accepted by XMage. Reconcile an uncertain acknowledgement before resuming. Expire queued actions on process restart.

**PM-MCP-05. AI seats.** Play against either the native XMage AI or an external Codex session through the private URL. Native AI requires no Codex connection. Ship a short Codex playbook that uses engine-confirmed choices, public archetype hypotheses and likely responses, plans conditional turn lines, and replans when interrupted. A hosted LLM opponent and benchmark claims about playing strength are outside this cut.

[Playmat WebSocket contract](../../WebSocketAPI.md) · [MCP Streamable HTTP](https://modelcontextprotocol.io/specification/2025-11-25/basic/transports)

### Decisions applied as beta defaults

The host starts manually. Replay access uses the player's perspective and no automatic opponent-hand reveal. Completed replays have no automatic expiration for the beta. Chat is live only. Metagame data starts with versioned curated public archetypes. Verify each of these defaults against implementation and preserve them in test fixtures. The first mobile release includes a browser flow and a real-device acceptance check. These defaults can be revised without changing the confirmed provider and format choices.
