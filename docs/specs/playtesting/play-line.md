# Semantic play lines

## PM-LINE-01 — Submit a complete justified line
A seated agent submits ordered `play_line` actions from its observed game ID and cursor. A line can begin in either player's turn. It supports the existing semantic play, attack, pacing and engine choice inputs. An exact observed choice and its optional value must have the same coverage as the low-level decision tool. A guarded future choice may use a currently knowable selector. The game validates each action at its actual prompt. The executor handles routine handoffs and ends the line at a significant opponent action, new information, a required choice not covered by the line, a configured stop, or an invalid action. Accepted actions stay applied.

After inspecting the current hand, a seat may submit an exact London bottom choice, a guarded Keep and its first land together. Once the engine accepts Keep, the line may cross the seat's own first upkeep and play the land at the next legal main-phase opportunity. An opening line can also start at an observed Keep. A fresh hand, a newly revealed card, an unplanned decision, an opposing start or a public response returns control before the land. From an observed casting prompt, a line may resume exact targets and mana payment for its face-up, unpaid, unresolved spell. It returns control after a reveal. A draw in a trigger's condition describes an event that already happened. Inspect the triggered effect for draws and other new information. An attack may declare its exact own triggers at confirmation. A trigger-order prompt publishes source identity and rule text for a face-up source on a visible battlefield. Its choice can identify that public source and an exact label. A source shared by multiple matching options is ambiguous.

## PM-LINE-02 — Pass with an explicit destination
A terminal `pass_until` action accepts `destination: "my_upkeep" | "my_draw" | "end_step" | "current_turn"` and `policy: "if_no_play" | "decline_optional"` (default `if_no_play`). Upkeep refers to the next own turn and returns control before drawing. Draw refers to the forthcoming own draw, including the same turn when called before the draw step. It returns control at the first actionable state after the draw boundary. The managed MCP engine seat requests explicit priority in its own upkeep and draw steps. A current-turn destination matches every supplied phase, step or priority condition. When the requested window is skipped, report the actual boundary. A required replacement choice during the draw step stays open until the pilot answers it.

A standalone terminal pass advances at ordinary priority when the only legal options are a pass and plain mana abilities. Rival actions, stack and board changes, and new information can occur between these passes. The `if_no_play` policy returns control when a meaningful optional play is available, including free spells and abilities with significant non-mana effects. When `stopOn` is omitted, the line retains its existing interruption reasons at meaningful options and when verifying an earlier action, observed combat, an adopted stack, or a decline bound to a particular decision. The `decline_optional` policy lets a pilot yield when a response is legal without publishing the policy.

A terminal pass can supply `stopOn`, an array of distinct events. Each enabled event interrupts the pass with its matching reason, even at a priority window that only offers a pass:

- `new_information` uses information that became visible to this seat. A rival's hidden draw does not qualify.
- `new_spell` uses a new cast by the opponent. Playing a land, activating an ability, placing a trigger, or already having an object on the stack does not qualify.
- `attackers_declared` uses a new opposing attacker declaration. Entering the combat step, reading an existing attack, or observing a subsequent attack trigger does not qualify.

Filters apply to events after the terminal pass starts. `stopOn: []` with `decline_optional` yields ordinary priority up to the requested destination, subject to mandatory decisions and execution guards. The requested destination retains its prompt, including a required choice at that boundary. The normal own draw completes `my_draw` even with a `new_information` filter. An earlier extra draw cannot satisfy a skipped turn-based draw when the engine supplies the draw witness. The executor also returns control for an unplanned required decision along the way and ends or invalidates execution when the game ends or rollback changes its scope. Intermediate passes preserve their guarded execution and reject `stopOn`. A terminal `pass_priority` makes one deliberate ordinary pass and returns at the next actionable boundary without making another pass.

When `my_draw` follows earlier actions in the same line, its destination is chosen from the state after those actions. An already-skipped opening draw cannot prevent a line that just played a land from passing toward the next actual draw.

Without an explicit terminal `stopOn`, an automatic pass stops before the turn-based draw when the public rules of a visible battlefield source indicate that the draw can trigger an ability and the last upkeep priority offers a meaningful play. This applies on either player's turn. A fresh action at that boundary can deliberately cross it. An explicit `stopOn` uses the selected event policy, and `if_no_play` still returns control at meaningful optional plays. The guard uses battlefield information published to the acting seat. Public delayed effects outside that projection and conditions that require additional engine state have limited coverage.

## PM-LINE-03 — Return the next decision in the same response
A line returns state and a receipt together. Within a bounded wait, return once the executor completes or interrupts. If the wait expires, return the same plan identity, current progress and seat-visible state, marking that the plan still owns execution. The client may wait for that plan's meaningful stop through the decision-wait tool. A transport cancellation ends the wait while preserving the receipt of any accepted line. Retrying an identical command ID in the same active seat process returns its receipt without replaying actions. Reuse with a different payload rejects. A stale or foreign request cannot affect an active plan.

## PM-LINE-04 — One bootstrap
A single guide request loads the core guide, well under client tool-output limits, and indexes the detailed guides, which load by ID. Guide loading and tool descriptions teach agents to submit the longest line justified by current information and stop to replan at a new decision. Existing tools remain available to compatible clients.

### PM-LINE-STRATEGY-1 — Reach the same matchup advice

A fresh match or tournament pilot discovers `matchup-strategy` in the core bundle and can read it before making material tactical decisions. Coaching and the authorized replay prompt point to or include the same source. A tournament seat's assignment includes the name, revision and known archetype of its own registered list. The assignment never publishes the opponent's deck metadata before normal publication. A missing archetype leaves the variant's strategy uncertain.

## Live playtest acceptance

- **PM-LINE-FLOW-1** Casting a modal spell with a confirmed deterministic mode can retain the planned continuation. A mode that reveals previously unavailable cards returns control before a later tactical action.
- **PM-LINE-FLOW-2** A planned decline of a known optional payment can retain the continuation when that branch reveals no new information. Accepting the discard-to-draw branch still requires inspection when the new card becomes visible. The answer must match the legal prompt.
- **PM-LINE-FLOW-3** A pass from an observed stack can advance to the first meaningful boundary. A terminal pass can advance past ordinary priority when only a pass or plain mana is available. The declared terminal stop events and the requested destination still return control. A following tactical action remains guarded by rival actions, uncovered required decisions, and newly visible material information. An opponent's hidden draw and a draw visible to the acting seat are distinct.
- **PM-LINE-FLOW-4** Own expected triggers can be attached to an observed own resolving source, including a spell whose payment is already pending. Prepared copies and deterministic public triggers can carry a continuation when their source, causality and result are confirmed. During an automatic pass, a rival triggered ability whose source was a face-up public battlefield or command-zone object when the line began is not a rival action: the line lets it resolve unless it targets a permanent or spell, needs reevaluation for new information, asks the seat for a choice or, under `if_no_play`, meets a legal response.
- **PM-LINE-SEM-1** A mana payment can identify a source and color without reproducing its printed rules. It follows the legal engine option and preserves its actual side effects, including painland damage.
- **PM-LINE-SEM-2** A mode, spell ability, alternate cost or cast face can select a unique legal engine option from the same cast. A line announcing a Room's door can pay for that same face and continue through its planned actions. A changed or ambiguous option leaves the next decision unapplied.
- **PM-LINE-SEM-3** Exact targets can be matched to their projected role or visible zone without reproducing a localized prompt. Distinct mandatory target prompts remain distinct. The engine may choose the sole legal opponent for a mandatory target-opponent role when auto-targeting is enabled. A cast can continue past a target role whose exact public selection is already proven by the same spell instance.
- **PM-LINE-SEM-4** Mana-only priority does not interrupt safe passing. A separate legal non-mana play, including an alternate cost, still does.
- **PM-LINE-SEM-5** One typed activation selects an exact non-mana ability of an owned visible battlefield permanent. A line can pay declared mana, select legal targets and continue after the exact activation resolves. The current priority choice supplies the legal ability ID and, when identifiable from a unique public rule, its full source-named `abilityText`. A short summary with an ellipsis or `{this}` cannot substitute for that rule. Ambiguous summaries expose no inferred rule. A mismatched picker, stack object or opponent action interrupts the line.
- **PM-LINE-MCP-1** An agent can distinguish schema rejection, preflight rejection and a running or interrupted line using a stable code and execution evidence. A lost response is recoverable by the same command ID.
- **PM-LINE-MCP-2** Compact state is discoverable via the native MCP schema and retains the IDs, legal choices and current priority needed to continue. Connected catalog exposure requires separate verification.
- **PM-LINE-COMBAT-1** A line can submit and confirm exact legal blocker assignments. Combat can continue after confirmed damage between observed combatants or exact life loss from an observed unblocked attacker. A rival action or unexplained combat change returns control.

- **PM-LINE-FLOW-5** An exact answer to a public trigger-order prompt can opt into following its selected trigger and the final forced trigger. The engine must confirm the public source, ability, instance and placement order. Unknown, changed or additional stack objects, meaningful rival actions, and new information still return control.
- **PM-LINE-FLOW-6** Without an explicit terminal `stopOn`, a queued pass returns control before an applicable public draw trigger when the relevant upkeep offers a legal non-mana play. Priority with just a pass and plain mana continues. A draw destination with no applicable trigger can reach the draw. A new command from the returned position can pass deliberately. A terminal pass with explicit `stopOn` and `decline_optional` can cross that upkeep using its selected event filters.
- **PM-LINE-IMPULSE** A line may cast a known creature, use its exact single-faced object ID in the next spell’s target and own trigger forecasts, order its announced pair, and expose the new exiled card. Binding requires a witnessed resolution of that specific creature spell and the same face-up, controlled permanent carrying its caster-only entry witness. A second copy, counter, reentry, control change or replacement cannot satisfy that binding. A known ordering prompt still requires its declared or observed choice. Return before passing the next stack object, attacking or using the exiled card. An advance that explicitly declines known options still stops at the reveal. While the targeting spell is on the stack, an instant with an alternate cost can be playable immediately. A zero-cost creature or a land may first become playable after that spell resolves. Comparing the current legal buttons or checking untapped lands cannot establish that the later choices are unchanged.
- **PM-LINE-IMPULSE-WAIVER** On its own turn a seat may explicitly forgo one face-up card from its own specified Valiant trigger for the remainder of this command. The source, triggered stack instance, resolution and single library-to-exile movement must agree. The command may declare its fixed attackers and pass until priority in its own end step, even if this card is free. Any other information, intervention, prompt, legal option, changed incarnation or missing witness interrupts before another submission. A retry has the same consent and receipt. Without this opt-in PM-LINE-IMPULSE applies.
- **PM-LINE-SEM-6** An optional casting-cost question can be answered with a guard for the exact visible source and engine question. Queue that choice at the engine's observed point in the announcement, before targets for Burst Lightning. A `play` action's `optionalCosts: "pay" | "decline"` answers every "Pay … ?" optional additional cost question asked by that exact cast. Taking the cost preserves the engine's resulting payment and information boundaries.
- **PM-LINE-SEM-7** A `playAs:"land"` action requires one matching engine choice marked `canPlayLand:true` when it executes. At an empty-stack main-phase priority decision with zero matching land choices, the line interrupts with `land_play_unavailable` before applying the land or later actions. Multiple matching legal choices retain `ambiguous_choice`.
- **PM-LINE-MCP-3** A line supports at most one terminal pass. A `pass_priority` and any cross-turn or end-step destination must be last. An intermediate `pass_until` requires `destination: "current_turn"`, a named engine phase or step, `priority: "self"`, and an immediately following play, activation, choice or combat declaration. A combat action requires the step of its own declaration or `BEGIN_COMBAT`, from which it waits for the next matching declaration in this turn. If the engine skips the declaration or priority has already opened after it, stop before consuming that priority. A phase alone cannot select a combat declaration. The requested policy governs passes on approach and from beginning of combat to the declaration. A missed window or an undeclared decision preserves the remaining actions. An unavailable play at the window cannot execute later. Preflight rejects a premature pass with `bad_sequence`, the action index and the one-pass rule before applying any action.

- **PM-LINE-COMBAT-2** An attack can identify an exact observed player, planeswalker or battle for each creature. A plain attacker list attacks the sole opposing player when XMage also offers planeswalkers or battles. A token that an expected own attack trigger creates tapped and attacking joins the defender of that trigger's source, or the attack's `tokenDefenderId`. The engine must witness the declared assignments before confirming them. Verified damage to a planeswalker or battle can continue through the associated counter change, including lethal loyalty loss and the resulting graveyard move. Other effects and decisions still require independent evidence.

- PM-LINE-02: safe passing sees free plays, explicit decline can hold up mana, and upkeep and draw have distinct observed boundaries. ### PM-LINE-REPLAY-1 · Player-authored line explanations

An authorized pilot may omit commentary or supply an authored `explanation` on either `play_line` or `play_turn`. Accept 1–4,000 Unicode code points after trimming. For material plays, the MCP guide uses Markdown bullets for the chosen line and intended objective, one or two credible alternatives and their costs, and the contemporaneous public fact that decides the comparison. Report resolution only after the receipt and public board support it. Follow the host's chat mode and answer pending engine decisions before writing commentary. A short comment suffices for a routine play. The native MCP schema and worked Markdown example are covered by `[PM-LINE-MCP-2] the turn guide examples pass the published native MCP input contracts` in `ops/playtesting/mcp/test/play-line-http.test.mjs`.

The first dispatched decision records one `kind:"line"` event at the current replay frame with the authenticated player, timestamp, command ID, `audience:"public"` and `explanation`. A turn uses its sequence ID. A rejected line without a dispatch creates no entry. Receipt recovery cannot publish the line again. Changing its text under the same command ID conflicts.

Public spectator frames and public, seat and full replay frames may include explicitly published explanations. Project only the text and presentation metadata. A bounded live feed and the archived feed identify the same event; identical command IDs from different seats identify different events. Table talk remains a separate event. Spectator explanations do not produce a table-chat message, unread notification or chat cursor.

The existing `play_line.reasoning` accepts 1–600 characters as before. Callers may supply one commentary field per line. Delegated broadcasts may show legacy entries. Seat replays retain their own legacy notes and authorized full replays retain notes from both players. Missing publication markers on existing records never grant public access. Older archives require no migration.

**PM-LINE-REPLAY-2 · Markdown presentation.** Live spectator and replay commentary render Markdown headings, paragraphs, emphasis and lists. Existing prose remains readable. A `card://` link continues to open the card preview through pointer, keyboard and touch interaction. Renderer input cannot introduce raw HTML elements, remote media requests or navigable outside links.

### PM-LINE-WAIT-1 · Command delivery and destination

A zero-duration initial receipt followed by a bounded wait for the same game and command authorizes the same actions and destination as a single long initial wait. A command waiter wakes when its line stops, even before another own prompt. The terminal receipt reports execution ownership, the current seat decision, the witnessed destination or interruption and the frozen executor timing. A rollback takes precedence. Each HTTP wait can expire while the command remains running.

### PM-LINE-WAIT-2 · Opening transition and active execution time

Explicit opponent priority without an own prompt suspends the active budget. A successful acknowledgement of an exact own opening Keep permits waiting for the first turn within the same game and epoch. A fresh own prompt restores active accounting and uses the usual guards. A first opposing turn, new information or a changed epoch interrupts before a queued land. Generic absence of a prompt consumes active time. All sequences retain their maximum wall lifetime. The receipt exposes time under opponent priority, the acknowledged opening transition and other active execution. These observations do not identify a player's thinking time.

`test/line-wait-contract.test.mjs` instruments both client delivery patterns, slow opening, unknown waits and lifetime limits. `product/london-mulligan.local.mjs` compares the two deliveries for the same seeded Pioneer turn via native MCP and isolated Java XMage.


### Payment references and single priority passes

- **PM-LINE-PAY-REF** At own priority and at an engine mana-payment prompt, each visible own source offered for mana exposes copyable `payWithOptions` entries containing its exact object ID and any observed ability ID and color. Source order belongs to the pilot. A current payment choice also exposes a `playLineAction` bound to the current decision and choice IDs. A source click can open an ability or color picker.
- An immediately available play or activation with a payment object ID absent from a complete visible position is rejected before announcing it. The rejection returns the action and payment indices, current state, and zero applied decisions. Later announcements are checked only when reached, after earlier land plays or other changes. If XMage omits a declared source from the actual cost prompt, the executor stops with `source_unavailable`, applied progress and the current choices. A previous use or tapped status alone does not make a source unavailable. Rules and ability choices may allow reuse.
- **PM-LINE-STACK-PASS** At an actionable own priority prompt with a nonempty stack, the engine's legal pass choice exposes `playLineAction: {"kind":"pass_priority"}`. Sending that action grants a single pass. A new rival response stays visible for the pilot's next decision. Rendering the action never submits it.

- **PM-LINE-COPY** At actionable own priority, a visible engine land option exposes its exact zone and object ID with `playAs:"land"`. A verified legal spell exposes a `play` action, with `when:"priority"` when responding outside an empty-stack own main phase. An own battlefield ability requires its observed unique ability ID and full public ability text. A group with multiple abilities keeps each verified action on its own ability entry. The pilot can add known costs/targets and retain the rest of the line. A pending choice still returns control. Other players' priority, a face-down object, a pending rollback or a running command cannot grant a new priority suggestion.
- At the pilot's attacker or blocker declaration, each projected button/object has a prompt-bound choice. The engine's actual all-attack button sends one choice, preserving defender selection and confirmation. An earlier declaration's choice cannot act on a later prompt. Missing controls do not synthesize an all-attack action.

### PM-LINE-RECOVERY — Safe continuation of a stopped line

Both compact and full line receipts expose `nextAction`. Its `appliedDecisions` counts acknowledged engine decisions for the submitted command. A preflight or action-schema rejection counts zero. An error with unknown completion uses null. A verified seat projection can supply the current cursor and decision ID. A pending command returns a command-specific wait without cursor filters. A pending rollback, unavailable seat, uncertain acknowledgement and end of match each have their own continuation.

On an actionable panel the `play_line` arguments contain one `choose` pinned to the observed decision. The pilot fills `requires` with a fresh command ID and their choice. Numeric and distributed numeric prompts also require a value. A request with unsupported action fields returns their paths and applies zero decisions. Registered-player and human-table calls preserve the original seat selector. The HTTP integration cases tagged `PM-LINE-RECOVERY` cover numeric X, the following payment panel, partial acceptance, command recovery, disconnection, acknowledgement loss and seat authorization.
